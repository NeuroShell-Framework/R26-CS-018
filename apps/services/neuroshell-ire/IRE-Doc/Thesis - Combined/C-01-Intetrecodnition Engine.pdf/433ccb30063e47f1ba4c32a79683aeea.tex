\protect\hypertarget{_Toc900001}{}{}ABSTRACT

Large language models (LLMs) are increasingly used to translate
natural-language security requests into machine-executable actions.
Their stochastic outputs, however, can contain malformed structures,
hallucinated parameters, out-of-scope targets and adversarial content,
creating safety risks when connected to automated security tools. This
thesis presents the Intent Recognition Engine (IRE), a component of the
NeuroShell framework that converts free-form instructions for four
security tools (Nmap, Gobuster, Nikto and Nuclei) into validated intent
contracts. The IRE combines an offline, CPU-based language model with a
multi-stage pipeline and deterministic validation, so that invalid or
unsafe outputs are rejected before downstream processing.

The engine was evaluated on 1,500 records using two offline backends,
Gemma and Qwen, with ablation testing to isolate individual layers.
Relative to unguarded model output, the guarded pipeline raised decision
accuracy from 78\% to 86\% (Gemma) and from 69\% to 82\% (Qwen), raised
the flawed-input catch rate from 0\% to 72\% and 64\%, and reduced the
false-positive rate from 32\% to 14\% and from 31\% to 15\%. The
deterministic validation stack was the dominant contributor to safety:
removing it lowered catch by 30 and 24 percentage points. Catch was
strongest for flaw classes with a decidable signal (78--100\%) and
weakest for contradictory, out-of-scope and ambiguous requests
(40--59\%).

These findings indicate that small, locally deployed language models can
support safer security-copilot workflows when constrained by
deterministic validation and a closed trust boundary. All results are
single-run point estimates obtained on one CPU-only machine, which
limits cross-platform generalisation. Future work should improve
protection of the semantic classes, extend tool support, and validate
the framework in operational settings.

\textbf{Keywords:} Intent Recognition, LLM Guardrails, Hallucination
Detection, Offline Language Models, Security Copilots

\hypertarget{chapter-1-introduction}{%
\section{CHAPTER 1: INTRODUCTION}\label{chapter-1-introduction}}

This chapter introduces the research reported in this thesis. It
describes the context of the NeuroShell framework and of the Intent
Recognition Engine (IRE) on which the thesis concentrates, states the
problem and the research gap, and defines the aim, objectives and
research questions. It then delimits the scope, limitations and
assumptions of the study, clarifies the author's individual
contribution, and outlines the organisation of the remaining chapters.

\hypertarget{overall-project-context}{%
\subsection{1.1 Overall Project Context}\label{overall-project-context}}

Modern security operations rely on specialised tooling to discover,
assess and remediate faults across networks and applications. As the
scale of this work grows, the manual translation of an operator's intent
into safe, well-scoped tool actions becomes a significant bottleneck.
Errors introduced at this point, such as an incorrect target, a
malformed instruction or an out-of-scope action, can affect production
infrastructure. Large Language Models (LLMs) are attractive for this
translation step because they can interpret natural language and emit
structured, machine-readable instructions that drive security tooling
{[}1{]}. However, a language model is a stochastic component: its output
may be malformed, misclassified or hallucinated, or it may be the
product of injected instructions. A security pipeline that acts on such
output without further checking transfers each of these errors into the
actions it executes.

NeuroShell is an autonomous, natural-language-driven security
orchestration framework developed as a four-component research chain
(project reference R26-CS-018). Its components are the Intent
Recognition Engine (IRE), a Dynamic Planner, an Adaptive Execution and
Error Recovery engine, and an AI-driven Vulnerability Analysis engine,
as shown in Figure~1.1. The framework allows an analyst to express
offline security tasks in natural language and uses the resulting
validated, structured contracts to drive downstream automation within an
explicitly configured engagement scope. It therefore lies at the
intersection of cybersecurity automation, software engineering and
applied machine learning. A central concern of the framework is the
first step of the chain: the point at which human intent is converted
into a machine-executable form. An error introduced at this point
propagates through every subsequent stage and must be detected before it
takes effect.

\includegraphics[width=5.625in,height=3.35685in]{vertopal_433ccb30063e47f1ba4c32a79683aeea/media/image1.png}

\protect\hypertarget{_Toc900009}{}{}\textbf{Figure~1.1:} Overview of the
NeuroShell framework and the position of the Intent Recognition Engine

This thesis concentrates on a single component of the framework. It asks
whether, in an offline, CPU-only deployment, a small instruction-tuned
language model can be made sufficiently reliable to serve as the head of
an automated security pipeline when its raw output is constrained by
deterministic validation.

\hypertarget{individual-component-context}{%
\subsection{1.2 Individual Component
Context}\label{individual-component-context}}

The IRE is the first component of the chain (Component 01). It acts as a
domain-specific Natural Language Understanding (NLU) gateway: it
receives natural-language security commands, for example a request to
perform a targeted network discovery scan, and returns a structured,
validated intent contract that downstream components consume without
re-interpreting prose.

The component boundary is deliberately narrow. The IRE is concerned with
understanding and validating \emph{intent}; it does not decide how a
task is scheduled, across which hosts it runs, or how execution failures
are recovered. These responsibilities belong to the Dynamic Planner
(Component 02) and to the Adaptive Execution and Error Recovery engine
(Component 03), which consume the output of the IRE. The handoff is
designed to be safe by construction: the output contract carries an
explicit intent type, a resolved target, the recognised options and any
validation findings, and the downstream contract requires that actions
derived from rejected intents must not be executed.

Because the IRE sits at the head of the chain, its reliability bounds
the reliability of the components that follow. A mislabelled target, a
misclassified intent or an accepted hallucinated identifier would be
inherited by every downstream action. The IRE therefore couples an
instruction-tuned language model with deterministic validation and guard
stages whose purpose is to contain model error before it can propagate
to the planner or executor. This thesis evaluates whether this guarded
design achieves intent recognition that is sufficiently accurate and
error-resilient to justify acting on model-produced security
instructions in a controlled, offline setting.

\hypertarget{problem-statement}{%
\subsection{1.3 Problem Statement}\label{problem-statement}}

Security operations are constrained by the manual translation of
operator intent into tool actions. A penetration tester or analyst must
map free-form instructions, such as ``scan the internal network for
EternalBlue'' or ``check this host for CVE-2021-44228'', onto commands,
targets and constraints while respecting authorisation boundaries.
Recent work shows that LLMs can act as capable copilots for parts of
this work, producing realistic attack plans and driving tools in
controlled environments {[}1{]}, {[}2{]}. Using an LLM for this
translation is attractive because natural language is the operator's
native interface.

The difficulty is that a language model is not a reliable translator.
Its output can be malformed, misclassified or entirely fabricated: LLMs
hallucinate identifiers and parameters {[}3{]}, and they can be diverted
by adversarially crafted utterances {[}4{]}, {[}5{]}. In a purely
conversational copilot, these errors appear as displayed text that a
human can vet. In an \emph{automated} security pipeline, where intent is
converted directly into actions, each such error becomes a candidate
machine-dispatched action: a fabricated CVE is looked up, a wrong target
is scanned, or an injected instruction is obeyed. Acting on unvalidated
model output therefore transfers every residual error of the model into
the security toolchain that it drives, as illustrated in Figure~1.2.

\includegraphics[width=5.20833in,height=4.11626in]{vertopal_433ccb30063e47f1ba4c32a79683aeea/media/image2.png}

\protect\hypertarget{_Toc900012}{}{}\textbf{Figure~1.2:} Handling of
model output in (a) an unvalidated pipeline and (b) the guarded pipeline
investigated in this thesis

The intent-recognition step concentrates on this risk. A copilot that
passes raw LLM output to a planner and an executor must, at a minimum,
emit a well-formed, schema-conformant and authorised intent structure
before any downstream component acts on it. Unless this structured
output is validated deterministically, the entire framework inherits the
failure modes of the model. This thesis addresses the resulting problem:
\emph{how can a small, offline, CPU-only language model be made
sufficiently reliable to serve as the intent-recognition head of an
automated security pipeline, when its raw output is constrained by
deterministic validation rather than by a human reviewer or a cloud
back-end?}

\hypertarget{research-gap}{%
\subsection{1.4 Research Gap}\label{research-gap}}

Three related gaps motivate this work. They are discussed below and
summarised in Table~1.1.

First, LLM copilots for security tooling validate their output
informally, if at all. PentestGPT decomposes penetration-testing tasks
across cooperating LLM-driven modules, but it does not subject its
output to deterministic schema, scope or authorisation validation before
machine consumption {[}1{]}. The sparring-partner systems demonstrated
by Happe and Cito {[}2{]} produce plausible next actions that are
consumed by a human. When the output of a copilot is fed to an
\emph{automated} toolchain, which is the natural integration point for
intent recognition, the requirement changes from plausibility to
correctness: a hallucinated CVE, a malformed structure or injected text
becomes a machine-dispatched action rather than displayed text. The
OWASP Top 10 for LLM applications catalogues prompt injection, insecure
output handling and related risks as first-class application concerns
{[}6{]}, yet the systematic defence of machine-consumed intent remains
largely unaddressed in the copilot work surveyed in Chapter~2.

Second, the defence literature either assumes interactive, cloud-hosted
generation or follows a retrieval-augmented route. Sampling-based
methods for detecting fabricated output, such as SelfCheckGPT {[}7{]},
semantic uncertainty {[}8{]} and semantic entropy {[}9{]}, together with
sampling-based self-consistency decoding {[}10{]}, all assume repeated
or interactive generation with generous compute. Retrieval-augmented
generation {[}11{]} grounds answers in external data, but it introduces
retrieved content as a prompt-injection surface {[}4{]} and requires
corpora and embedding infrastructure at inference time. The operational
setting targeted in this thesis is a small offline model running
unattended on an operator's laptop, with a latency budget that rules out
a retry loop or a verifier LLM. This setting is therefore not covered by
direct prior measurements.

Third, to the best of the author's knowledge and based on the review in
Chapter~2, no existing autonomous penetration-testing framework provides
a dedicated, isolated natural-language understanding layer that reliably
converts free-form offensive-security instructions into validated,
schema-constrained machine contracts. Existing tools either accept
structured input or rely on general-purpose LLMs without domain-specific
validation. Delegating this step to a general chat model without a
purpose-built validation layer is precisely the unsafe pattern
identified above. The research gap addressed by this thesis is therefore
the design and \emph{measurement} of a guarded, retrieval-free
intent-recognition engine, an isolated NLU component with deterministic
validation, for offline, single-device security deployments.

\hypertarget{aim-and-objectives}{%
\subsection{1.5 Aim and Objectives}\label{aim-and-objectives}}

The aim of this thesis is to design, implement and evaluate a guarded
intent-recognition engine that constrains the raw output of a small,
offline, instruction-tuned language model with deterministic validation,
so that the combined system can act as a reliable head of an automated
security pipeline in a CPU-only, single-device deployment. To achieve
this aim, four objectives are pursued.

O1. To design and implement the Intent Recognition Engine (IRE), a
component that receives free-text security requests and emits strictly
schema-conformant, authorised intent contracts, using a small offline
language model as a proposition generator whose output is validated
deterministically before it is handed onward.

O2. To construct a purpose-built evaluation data set of security prompts
that covers well-formed requests and deliberately flawed prompts across
the flaw categories that matter in practice (adversarial phrasing,
out-of-scope targets, ambiguous or contradictory requests, fabricated
parameters and identifiers, and role violations), with each prompt
annotated with gold labels.

O3. To establish an evaluation protocol that quantifies, using the
experimental results reported in this thesis, how much the guarded
pipeline improves structured intent recognition and flaw catching over
raw model output, and that ablates each guard layer independently to
estimate its individual contribution.

O4. To compare two offline language-model backends under an identical
guardrail stack, in order to measure how much of the achieved safety is
backend-independent rather than an artefact of a single model.

Each objective is addressed in a corresponding part of the thesis. The
relationship between the objectives, the research questions and the
chapters is summarised in Table~1.2 (Section~1.6).

\hypertarget{research-questions}{%
\subsection{1.6 Research Questions}\label{research-questions}}

The central question guiding this thesis is whether a small, offline,
unattended language model can be made reliable enough to drive an
automated security copilot once its output is subject to deterministic
validation. Three research questions are derived from this central
question.

\textbf{RQ1 (Pipeline value).} How much does a stacked validation
pipeline improve structured intent-recognition accuracy and flaw
catching compared with raw language-model output?

\textbf{RQ2 (Layer contribution).} Which individual guard layer
contributes most to the flaw-catch rate, and which layers, if any,
interact destructively when combined?

\textbf{RQ3 (Generalisability).} Do the guardrails generalise across two
different offline language-model backends, or is the measured safety an
artefact of a single model?

The study is an empirical, measurement-based investigation rather than a
hypothesis-testing one. The outcomes of RQ1 to RQ3 are quantified from
the experimental results reported in Chapter~6, and no claim of
statistical significance is attached to the single-run measurements (see
Section~1.7.2).

\subsection{1.7 Scope, Limitations and
Assumptions}\label{scope-limitations-and-assumptions}}

\hypertarget{scope}{%
\subsubsection{1.7.1 Scope}\label{scope}}

This thesis is an individual study of a single component, the IRE
(Component 01 of the NeuroShell framework, project reference
R26-CS-018). It does not implement the downstream planner, executor or
vulnerability-analysis components. Within this boundary, the scope
covers four elements: (1) a guarded NLU pipeline that accepts free-text
security requests and emits validated intent contracts; (2) the
deterministic validation and security countermeasures that constrain the
output of the model; (3) an offline, CPU-only, single-device deployment
in which nothing is retrieved at inference time and no request leaves
the device; and (4) a closed intent taxonomy and an operator-configured
engagement scope that bounds the permitted targets and techniques. The
evaluation is conducted on a curated, annotated data set of prompts in a
laboratory test harness rather than against live production traffic.

\hypertarget{limitations}{%
\subsubsection{1.7.2 Limitations}\label{limitations}}

The principal limitation is evidential. The results reported in this
thesis rest on a bounded experimental record of single-run point
estimates, without confidence intervals or seed sweeps, and therefore
carry residual uncertainty, which is discussed in Chapter~7. In
addition, only two offline language-model backends are compared under
the guardrail stack, and the evaluation data set was authored by the
researcher rather than drawn from observed operational traffic.
Measurements are specific to the evaluation hardware and the CPU-only
inference runtime, so latency and throughput figures are indicative
rather than generalisable. Finally, the framework-level benefit of the
IRE is validated only at the component level; end-to-end orchestration
with the downstream components lies outside the measured evidence
presented here.

\hypertarget{assumptions}{%
\subsubsection{1.7.3 Assumptions}\label{assumptions}}

The design and evaluation rest on the following assumptions.

• The operator configures the engagement scope and authorisation policy
correctly; the scope guard can enforce only the boundary that it is
given.

• The deployment device and the downloaded model weights are trusted;
physical compromise of the device and backdoors embedded in the model
weights are out of scope.

• Downstream components consume the intent contract as specified and
honour the contract rule that actions derived from rejected intents must
not be executed.

• Because the pipeline performs no retrieval and renders no free-form
output, indirect prompt injection via retrieved content and tool
injection via unfiltered rendered text are structurally out of scope.
This narrows the attack surface to the classification of the single user
utterance.

• The annotated prompts in the evaluation data set are representative of
the phrasing that an operator would use with the system.

\hypertarget{individual-contribution}{%
\subsection{1.8 Individual Contribution}\label{individual-contribution}}

This thesis is an individual study of Component 01 of the NeuroShell
four-component research chain. The author's individual contribution is
the design, implementation and evaluation of the IRE, and comprises five
elements:

(1) the architecture of the guarded NLU gateway, in which a small
offline language model acts as a proposition generator and deterministic
stages validate structure, target syntax and authorisation before an
intent is emitted;

(2) the security countermeasures layered around the core, including the
authorisation checks, the adversarial-utterance detection, and the

(3) the authoring of the annotated evaluation data set covering

(4) the evaluation harness and the per-layer ablation protocol used to

(5) the empirical comparison of two offline language-model backends

The other components of the NeuroShell chain, namely the Dynamic
Planner, the Adaptive Execution and Error Recovery engine and the
Vulnerability Analysis engine, provide the context in which the IRE
operates. They are described only to the extent needed to define the
interface contract of the IRE. The author takes responsibility for the
correctness of the IRE implementation and for every result reported in
this thesis.

\hypertarget{review-method-and-scope}{%
\subsection{2.1 Review Method and Scope}\label{review-method-and-scope}}

This chapter reviews the literature needed to answer the research
questions in Section~1.6. It is a targeted narrative review rather than
a formal systematic review, so screening statistics are not reported.
The review establishes (1) how language-model copilots for security
operations behave and validate their output; (2) the attack surface of
applications that integrate language models with tooling; (3) the
methods available for detecting fabrication and measuring agreement or
uncertainty; and (4) which of these remain viable under the constraints
adopted in this thesis, namely offline CPU-only operation, a strict
per-request latency budget and no retrieval at query time. These aims
map onto RQ1 to RQ3.

Sources comprise ACM, EMNLP, ICLR and NeurIPS publications, ACM
Computing Surveys, arXiv preprints and canonical technical sources (the
IETF RFC series, OWASP, and the Nmap and Metasploit documentation). A
work was included if it was relevant to at least one research question
and had a verifiable primary source reporting an empirical evaluation or
an authoritative specification. The machine-learning literature is
concentrated in 2019 to 2025, which spans the emergence of the
sentence-embedding and retrieval techniques discussed here {[}11{]},
{[}12{]}; older standards and tooling references are retained because
they define stable interfaces. Methods that assume interactive
generation, a cloud-hosted verifier or retrieval infrastructure are
included as the alternatives against which the guarded design must be
justified. Section~2.2 sets out the theoretical background, Section~2.3
the related research, Section~2.4 existing systems and techniques, and
Section~2.5 the resulting research gap and conceptual framework.

\hypertarget{domain-and-theoretical-foundations}{%
\subsection{2.2 Domain and Theoretical
Foundations}\label{domain-and-theoretical-foundations}}

\hypertarget{security-operations-and-intent-recognition}{%
\subsubsection{2.2.1 Security operations and intent
recognition}\label{security-operations-and-intent-recognition}}

Security operations comprise the systematic discovery, assessment and,
where authorised, remediation of weaknesses in networks and
applications. Operators work through a small set of recurring intents,
such as discovering exposed hosts, enumerating services and checking
whether known vulnerabilities apply to a target. These intents map onto
specialised tools, notably Nmap for network scanning {[}13{]} and
Metasploit for exploitation {[}14{]}. Two properties matter here. Each
intent carries a target and parameters, so the gap between prose and
machine dispatch is structural rather than cosmetic. In addition, every
action is bounded by authorisation: it may touch only targets and
techniques within a declared engagement scope, and some intents are
reserved for particular roles.

Intent recognition is a natural-language understanding (NLU) problem
that combines intent classification, which assigns an utterance to one
of a fixed set of classes, with slot filling, which recovers typed
values such as hosts, networks and ports. The intent contract
(Section~1.2) is the machine-consumable record of both steps and is
therefore expressed in a schema-bounded syntax. Sentence embeddings,
represented here by Sentence-BERT {[}12{]}, map strings into a vector
space in which semantically similar strings are close. They supply two
similarity signals used in this work: agreement between several model
outputs, and recognition of a repeated intent without re-invoking the
model.

\hypertarget{stochastic-generation-hallucination-and-uncertainty}{%
\subsubsection{2.2.2 Stochastic generation, hallucination and
uncertainty}\label{stochastic-generation-hallucination-and-uncertainty}}

Instruction-tuned language models generate by sampling: the model
defines a probability distribution over output sequences and a response
is drawn from it, so the same prompt can yield different outputs. A
single response is a sample of the model's belief, not a verdict, which
is why the IRE treats the model as an unreliable proposition generator
whose output is checked rather than trusted. Output can also be
fabricated. Ji \emph{et al.} {[}3{]} distinguish intrinsic
hallucination, which contradicts the input, from extrinsic
hallucination, which cannot be verified against the input or any
authoritative source. Fabricated CVE identifiers, addresses and ports
are of the extrinsic kind. Because downstream tools act on such values,
the practical requirement is to detect fabrication in tightly
constrained value spaces, where deterministic checking is feasible.

Detection without an external verifier relies on the statistics of the
model's own output. SelfCheckGPT scores the mutual consistency of
sampled responses {[}7{]}; semantic uncertainty and semantic entropy
measure disagreement across meaning-equivalence clusters {[}8{]},
{[}9{]}; and self-consistency decoding favours answers on which several
samples agree {[}10{]}. These methods ground the self-consistency gate
of the IRE, but every additional sample multiplies inference time, which
conflicts with a CPU-only latency budget. This tension recurs in
Section~2.5.

\hypertarget{authorisation-and-network-boundaries}{%
\subsubsection{2.2.3 Authorisation and network
boundaries}\label{authorisation-and-network-boundaries}}

Two foundations bound what a validated contract may assert. Role-based
access control (RBAC) derives authorisation from assigned roles and an
access matrix that grants or denies each intent per role; the four-role
model of the IRE follows this standard pattern. Network scope is
grounded in RFC 1918 {[}15{]}, which reserves address ranges for private
internets and so distinguishes internal from external targets. Together
with the declared engagement scope, these define what deterministic
validation can decide: syntax, format and authorisation are decidable,
and only meaning is delegated to the model. This division of
responsibility underpins the design in Chapter~4.

\hypertarget{related-research}{%
\subsection{2.3 Related Research}\label{related-research}}

\hypertarget{language-model-copilots-for-security}{%
\subsubsection{2.3.1 Language-model copilots for
security}\label{language-model-copilots-for-security}}

Two systems define LLM-assisted offensive security. Happe and Cito
{[}2{]} proposed language models as sparring partners for penetration
testing and demonstrated a closed-loop system in which a model drove a
deliberately vulnerable virtual machine to root access. PentestGPT
{[}1{]} decomposes an engagement across cooperating LLM-driven modules
so that each phase is planned and executed incrementally. Both show that
models can produce plausible security actions and operate tooling in
controlled environments, but both are generation-focused: output is
produced for a human reviewer and correctness is handled informally.
Neither subjects its output to deterministic schema, scope and
authorisation validation before machine consumption, which a copilot
feeding an automated toolchain must do. The IRE inverts this priority by
treating generation as a candidate that must satisfy checkable
predicates before it becomes an actionable intent.

\hypertarget{attacks-on-language-model-integrated-applications}{%
\subsubsection{2.3.2 Attacks on language-model-integrated
applications}\label{attacks-on-language-model-integrated-applications}}

Unvalidated model output is dangerous in integrated systems. Liu
\emph{et al.} {[}5{]} formalised prompt-injection attacks on
LLM-integrated applications and benchmarked common defences, concluding
that none was sufficient on its own. Greshake \emph{et al.} {[}4{]}
demonstrated indirect prompt injection, in which an attacker plants
instructions in content that an integration later retrieves and passes
to the model, and showed compromise of real-world assistant-style
applications. Kang \emph{et al.} {[}16{]} showed that dual-use attacks
built from standard computer-security techniques can bypass the
safeguards of deployed models with very high success rates. The OWASP
Top 10 for LLM applications lists prompt injection first among the risks
it treats as first-class application concerns {[}6{]}.

A security copilot that classifies an utterance with a model and
dispatches the result is exactly the integration these attacks exploit:
one adversarial utterance can steer the classification, and any
downstream consumer will act on it. The design response is to place
deterministic authorisation and validation \emph{after} generation, so
that even a fully diverted model cannot produce an accepted intent that
violates syntax, scope or role policy.

\hypertarget{fabrication-detection-uncertainty-and-grounding}{%
\subsubsection{2.3.3 Fabrication detection, uncertainty and
grounding}\label{fabrication-detection-uncertainty-and-grounding}}

The methods in Section~2.2.2 share an implicit budget: interactive
generation, or the freedom to produce and cluster several responses per
query. On a CPU-only model running on an operator's laptop, each extra
sample multiplies inference cost. This thesis therefore transposes the
disagreement intuition into a single guarded classification that
combines bounded sampling (a small number of responses), a cheap
embedding-based agreement gate and a deterministic escalation path that
needs no large verifier model.

A complementary line of work grounds answers in external corpora.
Retrieval-augmented generation (RAG) conditions generation on retrieved
passages so that answers can be traced to sources {[}11{]}, using
sentence embeddings for similarity {[}12{]}. It suits factual question
answering, but it places retrieved content in the prompt at inference
time, creating an additional prompt-injection surface {[}4{]}, and it
presupposes corpus and embedding infrastructure that contradicts the
offline, single-device boundary of Section~1.7. The IRE therefore
performs no retrieval and uses embeddings only for agreement and
caching.

\hypertarget{existing-systems-products-and-techniques}{%
\subsection{2.4 Existing Systems, Products and
Techniques}\label{existing-systems-products-and-techniques}}

This section assesses the systems and techniques that occupy the space
in which the IRE operates, using the inclusion criteria of Section~2.1.
Where an option is a technique rather than a product, the assessment
asks whether it is compatible with offline, CPU-only, retrieval-free
operation.

Deterministic tooling is mature. Nmap defines the host, port and service
values that a contract must carry {[}13{]}, and Metasploit parameterises
the most privileged class of intents {[}14{]}. Both expose structured
command interfaces and neither embeds a natural-language layer, so the
mapping from intent to command is performed by a human analyst or a
scripted wrapper, and authorisation policy must be wired in externally.
The copilots of Section~2.3.1 add natural language but remain
assistant-style tools whose consumer is human. Two integration
techniques are common in LLM automation generally: RAG, which widens the
attack surface through retrieved content, and tool calling, which binds
a model action to a machine effect with no intermediate validation
stage.

At the application layer, guardrail practice is codified by the OWASP
Top 10 for LLM applications, which lists prompt injection (LLM01) and
insecure output handling among its classes {[}6{]}. The defences
benchmarked by Liu \emph{et al.} {[}5{]} and the bypasses reported by
Kang \emph{et al.} {[}16{]} are post-hoc checks over model behaviour
rather than a deterministic stage between generation and dispatch. For
identifier values, the National Vulnerability Database (NVD) is the
authoritative CVE registry {[}17{]} and the Exploit Prediction Scoring
System (EPSS) scores exploitation likelihood {[}18{]}; a
fabricated-identifier guard would consult both if the offline boundary
were relaxed.

\hypertarget{gap-synthesis-and-conceptual-framework}{%
\subsection{2.5 Gap Synthesis and Conceptual
Framework}\label{gap-synthesis-and-conceptual-framework}}

The review converges on three findings. First, security copilots
{[}1{]}, {[}2{]} generate plausible actions for a human reviewer and do
not validate them for machine consumption. Second, applications that
integrate a model with tooling are exploitable through adversarial and
indirect-injection utterances, and the surveyed defences are
individually insufficient {[}4{]}, {[}5{]}. Third, fabrication-detection
and agreement methods {[}7{]}--{[}10{]} work in principle but assume
sampling or interactive generation whose cost conflicts with an offline
CPU-only latency budget.

The resulting gap is a combination that, to the best of the author's
knowledge, no surveyed system provides: a dedicated, isolated NLU layer
that converts free-form offensive-security instructions into validated,
schema-constrained, authorised machine contracts while running offline
and retrieval-free within a per-request latency budget. The surveyed
literature also does not measure the behaviour of a full guardrail stack
under that budget, the isolated contribution of each guard layer, or
whether the achieved safety transfers between offline backends. These
measurements are posed by RQ1 to RQ3, and this thesis addresses them by
designing and \emph{measuring} a guarded intent-recognition engine.

\hypertarget{conceptual-framework}{%
\subsubsection{2.5.1 Conceptual framework}\label{conceptual-framework}}

The design chapters rest on three principles drawn from Section~2.2,
summarised in Figure~2.1. First, the language model is a
\emph{stochastic proposition generator}: its output is a candidate,
never a decision, and sampling-based agreement {[}10{]} supplies a
confidence signal only. Second, responsibility is divided along the
decidability boundary: syntax, format and authorisation (schema, host
and CIDR syntax, port ranges, network and scope policy, role permission)
are decided deterministically, and only meaning is delegated to the
model. Third, the design enforces a \emph{safety invariant}: an intent
contract is accepted only if it is schema-valid, network-authorised, in
scope, role-permitted and non-adversarial. The model may propose any
candidate but cannot force acceptance of one that violates any of these
predicates. This reduces the open problem of making a single model
trustworthy to the closed problem of classifying one utterance under a
known policy, which justifies acting on model-produced instructions in
an automated toolchain. The framework also adopts the bounded-sampling
resolution of the cost tension in Section~2.2.2: a small number of
responses, an embedding-based agreement gate and a deterministic
escalation path (the hallucination validator) that needs no large
verifier model.

\hypertarget{from-framework-to-measurement}{%
\subsubsection{2.5.2 From framework to
measurement}\label{from-framework-to-measurement}}

The framework yields one measurable claim per research question. For
RQ1, the guarded pipeline raises the probability that output satisfies
the full conjunction of predicates relative to raw generation, measured
by intent accuracy, flaw-catch rate and false-positive rate with and
without the guards. For RQ2, ablating layers in turn against a constant
baseline isolates the largest safety contributor and the layers that
trade safety for usability. For RQ3, applying the identical stack to two
offline backends shows how much of the measured safety is
backend-independent. The evaluation protocol is developed in Chapter~3,
the implementation and test suite in Chapter~5, and the measurements in
Chapter~6.

\section{CHAPTER 3: RESEARCH
METHODOLOGY}\label{chapter-3-research-methodology}}

\hypertarget{research-design}{%
\subsection{3.1 Research Design}\label{research-design}}

This chapter specifies how RQ1--RQ3 are answered through measurement.
The thesis is a design-and-evaluation study in the design science
tradition {[}19{]}: an engineered artefact, the guarded
intent-recognition engine, is evaluated empirically under controlled
conditions, with a fixed protocol applied to an annotated data set by a
versioned harness (Section~3.7). The study is descriptive and
comparative; its outcomes are quantitative point estimates from a
committed experiment record, and no inferential claim is attached to
them.

\hypertarget{system-under-study}{%
\subsubsection{3.1.1 System under study}\label{system-under-study}}

The artefact (Figure~3.1) is a seven-stage core that converts a
free-form utterance into a validated intent, wrapped by five middleware
components under a two-sided role-based access-control (RBAC) policy.
Only the guard predicates matter for measurement, because their presence
or absence defines the treatment conditions; the full interface contract
is given in Chapter~4.

\includegraphics[width=5.69792in,height=3.09887in]{vertopal_433ccb30063e47f1ba4c32a79683aeea/media/image4.png}

\protect\hypertarget{_Toc900044}{}{}\textbf{Figure~3.1:} Guarded
pipeline and ablation targets.

Badges A1--A7 mark the components disabled in the ablation conditions;
A2 covers both role checks and A5 disables S5--S7 jointly.

Let \(\mathcal{X}\) be the utterance space, \(\mathcal{Y}\) the closed
intent taxonomy, \(\mathcal{C}\) the set of flaw categories,
\(\mathcal{R}\) the set of caller roles and \(\rho \in \mathcal{R}\) the
caller's role. The decoder is a stochastic map
\(f:\mathcal{X} \rightarrow \mathcal{Z}\) with output \(z = f(x)\); the
deterministic guards are the predicates \(g_{5}\), \(g_{6}\), \(g_{6B}\)
and \(g_{7}\) over the schema, regex/entity, network and scope stages;
\(b:\mathcal{R} \times \mathcal{Y} \rightarrow \{ 0,1\}\) is the RBAC
authorisation; and \(m_{1}\) is the adversarial-input detector. The
guarded decision is

\(\Phi(x) = \left\{ \begin{matrix}
y \in \mathcal{Y}\ \text{accepted}, & \text{if\ }G(z,x) \land b(\rho,y) \land \neg\, m_{1}(x), \\
e \in \mathcal{C}\ \text{rejected}, & \text{otherwise,} \\
\end{matrix} \right.\ \) (3.1)

where
\(G(z,x) = g_{5}(z) \land g_{6}(z) \land g_{6B}(z,x) \land g_{7}(x)\).
The design enforces the safety invariant that every accepted intent
satisfies every security predicate:

\(Accepted\left( \Phi(x) \right) \Rightarrow \bigwedge_{k \in K}P_{k}(x),\quad\quad K = \{ S5,S6,S6B,S7,RBAC,M1\}\)
(3.2)

Experiment~1 operationalises RQ1 as the gap in
\(\Pr\left\lbrack \bigwedge_{k \in K}P_{k} \right\rbrack\) between \(f\)
and \(\Phi\); Experiment~3 operationalises RQ2 as the change in catch
rate when a guard component is disabled.

design}\label{variables-and-experimental-design}}

Three factors are manipulated (Table~3.1): the pipeline condition (RQ1),
the backend (RQ3) and the guard configuration (RQ2). Experiments~1--3
use the full 1500-record set; Experiment~4 uses a deep-dive subset of

false-positive rate over the well-formed set and flaw-catch rate over
the flawed set (Section~3.4). All else is held constant: the data set
and record order, the hardware and CPU-only runtime, the sampling
parameters, thresholds, engagement scope, RBAC policy and per-stage
timeout, all pinned in the evaluation manifest (Section~3.7).

\hypertarget{experimental-procedure}{%
\subsection{3.3 Experimental Procedure}\label{experimental-procedure}}

Figure~3.2 shows the workflow. For each record, in fixed order, the
harness submits the request once per condition and records one decision.
The guarded condition returns either an accepted intent
\(y \in \mathcal{Y}\), only when the conjunction in Equation (3.1)
holds, or a rejection \(e \in \mathcal{C}\) with the assigned flaw
category. The raw condition (Experiment~1 only) records the model's
single-shot output with no guard; as raw output carries no rejection
category, it can never be classified as flawed. Each configuration is
executed once per backend.

\includegraphics[width=5.69792in,height=1.43947in]{vertopal_433ccb30063e47f1ba4c32a79683aeea/media/image5.png}

\protect\hypertarget{_Toc900050}{}{}\textbf{Figure~3.2:} Evaluation
workflow from data set to reported results.

In Experiment~3 the marginal contribution of component \(\mathcal{l}\)
is

\(\Delta{Catch}_{\mathcal{l}} = {Catch}_{\Pi_{\mathcal{- l}}} - {Catch}_{\Pi},\)
(3.3)

where \(\Pi\) is the fully guarded configuration and
\(\Pi_{\mathcal{- l}}\) the configuration with \(\mathcal{l}\) disabled;
a negative value shows that the component contributes to catch.
Condition A5 jointly ablates the validation stack and bounds its
aggregate contribution rather than that of a single layer.

The self-consistency gate adapts the sampling-based strategy of Wang
\emph{et al.} {[}10{]} to structured classification, in the spirit of
consistency-based hallucination detection {[}7{]}, {[}9{]}. For each
primary inference (temperature 0.4), \(k = 3\) further responses are
sampled at temperature 0.6, embedded as sentence vectors (cf. {[}12{]})
and compared pairwise:

\(\alpha(x) = \binom{k}{2}^{- 1}\sum_{1 \leq i < j \leq k}^{}1\left\lbrack d_{ij} \leq \theta_{s} \right\rbrack,\)
(3.4)

where
\(d_{ij} = 1 - cos\left( \mathbf{e}\left( z_{i} \right),\mathbf{e}\left( z_{j} \right) \right)\)
and \(\theta_{s}\) is the semantic threshold pinned in the manifest; a
raw single sample has \(\alpha = 1\) by construction. Insufficient
agreement routes the request to the hallucination validator, which
assigns one of six error classes (impossible CVE, impossible parameter
range, unverifiable value, contradictory fields, out-of-scope reference
or unresolved type) and applies a block, warn or escalate response;
\(k\) is fixed at 3 on latency grounds. The adversarial detector
precedes inference where possible: a cumulative suspicion score above
0.7 flags the request, and a score of at least 0.95 blocks it without
model inference.

\hypertarget{measures-and-evaluation-metrics}{%
\subsection{3.4 Measures and Evaluation
Metrics}\label{measures-and-evaluation-metrics}}

Let \(y^{\text{*}}(x)\) and \(c^{\text{*}}(x)\) be the gold intent and
flaw labels of record \(x\), and \(\widehat{y}(x)\) and
\(\widehat{c}(x)\) the intent and flaw category assigned by the system;
an accepted record carries an intent and no flaw category, and a
rejected record the reverse. A well-formed record that a guard flags
counts as not recognised, so it never inflates accuracy, and a flawed
record rejected under any other category counts as not caught. Intent
accuracy is computed over \(D^{\text{+}}\), with
\(1\lbrack \cdot \rbrack\) the indicator function:

\(D_{Acc} = \frac{100}{\left| D^{\text{+}} \right|}\sum_{x \in D^{\text{+}}}^{}1\left\lbrack \widehat{y}(x) = y^{\text{*}}(x) \right\rbrack.\)
(3.5)

The flaw-catch rate over \(D^{-}\) is

\(Catch = \frac{100}{\left| D^{-} \right|}\sum_{x \in D^{-}}^{}1\left\lbrack \widehat{c}(x) = c^{\text{*}}(x) \right\rbrack.\)
(3.6)

The criterion is strict: refusal under the wrong category is a miss, so
the metric rewards correctly diagnosed refusal, which a downstream
consumer needs. The false-positive rate over \(D^{\text{+}}\) is

\(FP = \frac{100}{\left| D^{\text{+}} \right|}\sum_{x \in D^{\text{+}}}^{}1\left\lbrack \text{a\ guard\ flags\ }x \right\rbrack.\)
(3.7)

A flagged request is a conservative over-block: the guard marks it for
scrutiny or rejects it, and never re-approves it as a different intent.
FP is the usability counterpart of the safety rates, and the design goal
is high \(D_{Acc}\) and Catch with low FP.

Each component's contribution to catch is the delta of Equation (3.3),
which isolates its marginal effect because everything else is held
fixed. Preliminary repeated runs of the ablation configuration indicated
a run-to-run variation of roughly ±1--2 percentage points, used as a
heuristic reading threshold (Section~3.5) and not as a confidence
interval. Operational cost is recorded as end-to-end latency per
cache-miss request, aggregated as percentiles per backend and
configuration, with cache-hit latency recorded separately; the figures
are reported in Chapter~6.

\hypertarget{ethics-privacy-security-and-responsible-ai}{%
\subsection{3.6 Ethics, Privacy, Security and Responsible
AI}\label{ethics-privacy-security-and-responsible-ai}}

The study involves no human participants and processes no personal data:
all records are author-authored synthetic requests, and none concerns an
identifiable individual. As no live system was affected, the study falls
outside work requiring institutional research-ethics approval; the
integrity declaration is included in Appendix~B.

The artefact, a natural-language gateway to security tooling, is dual
use by nature {[}1{]}, {[}2{]}, {[}16{]}. Three decisions bound the
risk: every action is subject to RBAC and scope enforcement, so by
Equation (3.2) an accepted intent is authorised and in scope before
downstream components act on it, on the declared assumption that they
honour the rejected-intent contract; evaluation ran offline on synthetic
prompts, contacting no live, third-party or production system; and
failure modes, including the weakness of the semantic flaw classes, are
published rather than suppressed.

The pipeline is offline and single-device, so no utterance or result
leaves the device. The threat model assumes an attacker who controls
only the user utterance, not the device, prompts, policies or weights,
consistent with the prompt-injection risks catalogued for LLM
applications {[}6{]}. Model output is treated as untrusted: it never
reaches a shell, and a per-stage timeout guards against a stalled model.
Reporting is equally conservative, with single-run point estimates,
declared limitations and a candid account of the safety--usability
trade-off. AI-based tools were used for language correction, drafting
support and artefact development, in accordance with institutional
policy (Appendix~B).

\hypertarget{reproducibility-and-research-artefacts}{%
\subsection{3.7 Reproducibility and Research
Artefacts}\label{reproducibility-and-research-artefacts}}

Every material behind the reported measurements is versioned with the
project source: the modular Python (FastAPI) service, the data set and
its generation script, the evaluation harness, the evaluation manifest,
the committed experiment record and the automated test suite (506 tests:
434 unit and 72 integration tests, as counted on 7 October 2026;
Section~5.4.2), which gates the harness. The manifest is the
authoritative anchor, pinning the Ollama version and model digests,
hardware, data set version, temperatures, \(k\), \(\theta_{s}\),
thresholds, scope, RBAC policy and timeout, so that no constant is
decided at run time. A single command regenerates every table of
Chapter~6, and the committed per-record decisions allow figures to be
audited without re-invoking the model.

Two boundaries apply. The model is stochastic, so an independent re-run
may differ slightly from the committed values, whereas the deterministic
guards reproduce exactly; and absolute latency is bound to the
evaluation hardware. The evaluation instruments are collated in
Appendix~A.

\hypertarget{requirements}{%
\subsection{4.1 Requirements}\label{requirements}}

\hypertarget{product-context}{%
\subsubsection{4.1.1 Product context}\label{product-context}}

NeuroShell IRE (the Intent Recognition Engine) is Component 1 of the
NeuroShell Core Framework, a language-driven security-automation stack.
The product is a domain-specific natural-language understanding gateway:
it converts a free-text offensive-security command into a validated,
schema-constrained intent contract that downstream components can
consume without ever receiving free-form model output. This
contract-first boundary is the central requirement of the product. Every
output exposed to the toolchain must be machine-validated, and no
unvalidated LLM text may reach it, as established in Chapters~1 and 3.

The IRE runs as a local daemon on the operator's device and serves other
components and human operators over HTTP. The complete framework places
two further safety gates downstream of the IRE: a planner that enforces
its own RFC 1918 and dangerous-pattern checks, and an executor that
performs recovery-driven command execution. The IRE is therefore
designed as the first, but not the only, enforcement point.

\hypertarget{local-offline-decoding-versus-a-hosted-model}{%
\subsubsection{4.3.1 Local, offline decoding versus a hosted
model}\label{local-offline-decoding-versus-a-hosted-model}}

The first architectural decision concerns the decoder. A cloud-hosted
model offers higher raw accuracy and easier scaling, but it contradicts
the product requirement that no request leaves the device and that no
credentials are held (Section~4.1 and Section~3.6). The adopted design
therefore runs a small model locally through Ollama in CPU-only mode.
This reflects the intended field deployment and keeps the trust boundary
on a single device. Two model backends remain configurable so that the
generality of the approach can be measured, as described in Chapter~3.

\hypertarget{structured-contract-versus-free-form-prose}{%
\subsubsection{4.3.2 Structured contract versus free-form
prose}\label{structured-contract-versus-free-form-prose}}

Raw LLM output is plausible prose, and a machine-dispatched action must
not be constructed from prose. The adopted design therefore forces the
model to emit a fixed JSON schema (S3) and validates the result through
stages S4 to S7 before anything is returned. Only an output that
survives all of these stages is exposed to the caller; any other outcome
returns a stage-specific, classified error. This decision converts a
plausibility claim into a verifiable one and underpins the guarded
decision function and safety invariant formalised in Chapter~3.

\hypertarget{deterministic-rules-versus-model-self-checking}{%
\subsubsection{4.3.3 Deterministic rules versus model
self-checking}\label{deterministic-rules-versus-model-self-checking}}

Two validation philosophies are available: asking the model to review
its own output, or recomputing the checks with deterministic rules.
Self-checking is prone to drift and reuses the same fallible estimator
that produced the output. The adopted design instead recomputes every
syntactic, network and scope check with deterministic code (S5 to S7 and
S6B) that depends on no further LLM calls. As a result, the
deterministic guard path is bit-exact and auditable, a property that the
reproducibility protocol in Chapter~3 relies on.

\hypertarget{no-retrieval-versus-retrieval-augmented-generation}{%
\subsubsection{4.3.4 No retrieval versus retrieval-augmented
generation}\label{no-retrieval-versus-retrieval-augmented-generation}}

Retrieval-augmented generation is a popular technique for grounding
model answers. However, retrieved text is itself a prompt-injection
vector {[}4{]}, and a retrieval channel enlarges the offline trust
boundary. The adopted design therefore performs no retrieval at
inference time; offline CVE grounding is loaded at start-up only. This
decision is what keeps the threat model closed, as discussed in
Section~4.4.5.

\hypertarget{two-phase-rbac-versus-a-single-check}{%
\subsubsection{4.3.5 Two-phase RBAC versus a single
check}\label{two-phase-rbac-versus-a-single-check}}

Role enforcement can be implemented as a single post-hoc check or as a
repeated invariant. The adopted design enforces RBAC twice: a
pre-inference fast-fail (M2) rejects restricted roles before any model
cost is incurred, and a post-inference check (M5) validates the final
intent against the role matrix. Consequently, bypassing a single guard
is not sufficient to manufacture an authorised action.

\hypertarget{self-consistency-versus-single-pass-confidence}{%
\subsubsection{4.3.6 Self-consistency versus single-pass
confidence}\label{self-consistency-versus-single-pass-confidence}}

The model supplies a confidence score, but calibrated confidence is
unreliable for small offline models. The adopted design therefore gates
low-confidence decisions through a self-consistency stage that samples
further responses and measures their agreement, accepting the resulting
latency cost only when the stage is triggered. The approach applies the
sampling-based agreement principle of self-consistency decoding {[}10{]}
to a single structured classification rather than to free-form reasoning
text.

\hypertarget{semantic-caching}{%
\subsubsection{4.3.7 Semantic caching}\label{semantic-caching}}

Identical intents recur in operator workflows. The adopted design
therefore adds a two-channel semantic cache, combining an exact hash
with embedding similarity, that short-circuits the LLM on a hit. Serving
a hit avoids model inference altogether, which reduces latency markedly
and improves determinism. The cache is invalidated when the offline
CVE-grounding database is reindexed, so that cached entries do not
outlive the grounding data on which they depend. Latency is one of the
performance measures defined in Chapter~3.

\hypertarget{detailed-design}{%
\subsection{4.4 Detailed Design}\label{detailed-design}}

\hypertarget{core-stages-s1-to-s7-and-s6b}{%

Stage S1 normalises casing, whitespace and Unicode (NFKC form) and
standardises jargon terms into canonical phrases. Stage S2 resolves
aliases, such as \emph{nmap -sS} to a SCAN action and exploit names to
canonical CVE identifiers, using the alias map in
\emph{data/alias\_map.json}. Stage S3 instructs the model to emit a
fixed JSON schema, at the sampling configuration pinned in the
evaluation manifest (see the reproducibility protocol in Chapter~3).
Stage S4 recovers the JSON payload by stripping code fences, markdown
artefacts and thinking tags.

summarises the checks that each performs. Stage S5 enforces the typed

produced, S6B applies engagement-scope and topology rules, and S7 acts
as the final enforcement gate. Because S5 to S7 recompute every check
without further model calls, a model output can be exposed only if it

\hypertarget{deployment-properties}{%
\subsubsection{4.4.5 Deployment
properties}\label{deployment-properties}}

The service runs headless and CPU-only, retrieves nothing at inference
time, and holds no credentials beyond the operator API key. Its only
persistent assets are the model weights, the authorisation policy, the
session context and the audit database. Because nothing is retrieved and
no free-form output is rendered downstream, the two principal remote
attack classes, indirect prompt injection via retrieved data {[}4{]} and
tool injection via unfiltered text, are structurally reduced to the
problem of classifying a single user utterance.

\hypertarget{professional-practice-and-ethics}{%
\subsubsection{4.5.2 Professional practice and
ethics}\label{professional-practice-and-ethics}}

Professional practice in this domain is chiefly the ethics of dual use.
Because the system can drive offensive tooling, the design gates every
such action behind role authorisation, a declared engagement scope and,
for the most sensitive flows, explicit human approval, and it restricts
targets to operator-declared private ranges {[}15{]}.

Responsible-AI practice is observed by treating the model as an
untrusted generator of propositions whose output is validated
deterministically and reported honestly (see Sections~3.5 and 3.6).
Capabilities, limitations and residual failure modes are published
rather than suppressed, as illustrated by the explicit register of
unimplemented capabilities in Table~4.11.

Accessibility is respected at the interface level, since the API returns
clear, structured responses rather than prose. Because the product does
not process personal data as part of its function, personal-data
protection regimes are not directly engaged. The applicable disclosures
and declarations are collated in Section~3.6 and in Appendix~B.

\hypertarget{component-implementation}{%

Implementation}\label{component-implementation}}

\hypertarget{pipeline-orchestration}{%
\subsubsection{5.2.1 Pipeline
orchestration}\label{pipeline-orchestration}}

The pipeline module instantiates every component and fixes their
execution order (Figure~4.2); the components and their implementing
modules are listed in Table~4.4. Each component sits in its own
exception boundary, so that a failure in non-critical middleware
degrades gracefully instead of aborting the request. Any component that
can reject a request does so with a classified error carrying the stage
name, the divergence field and the accumulated \emph{ValidationFinding}
entries.

At implementation level, S1 performs NFKC normalisation, control- and
thinking-tag removal and jargon standardisation; S2 maps 22 exploit
surnames, slang and tool terms to canonical identifiers; S3 uses
few-shot strict-JSON prompting with a 60 s timeout, a 2048-token cap and
a response cache; S5 is a typed Pydantic model that maps validation
failures to hallucination classes; S6 re-verifies IP, CIDR, CVE, port
and URL entities and rejects shell metacharacters; and S7 combines RFC
1918 private-address membership {[}15{]} with the engagement mode and an
injection re-scan. After the post-inference RBAC check (M5),
post-processing stores the result in the cache, assembles the response,
enriches it with the sub-intent and updates the session.

\hypertarget{contract-generation-audit-and-metrics}{%
\subsubsection{5.2.2 Contract generation, audit and
metrics}\label{contract-generation-audit-and-metrics}}

The contract builder synthesises the \emph{PlannerContract}: a
sub-intent classifier assigns each valid response a hierarchical
sub-intent that selects the tool (for example,
\emph{NETWORK\_SCAN.SYN\_STEALTH} maps to \emph{nmap -sS}), modifiers
are mapped to flags, and exploitation flows are marked for human
approval. The audit logger writes every finding to an append-only SQLite
database with SHA-256-hashed operator content, and the metrics collector
records latency percentiles, per-stage error counts and the intent
distribution.

harness}\label{strategy-and-evaluation-harness}}

Verification separates unit-level determinism from integration-level
wiring. Unit tests cover every guard path, every cell of the RBAC
matrix, both semantic-cache paths, all six hallucination classes and the
metric calculations, with the language model mocked so that the suite is
deterministic; model-dependent behaviour is measured by the evaluation
harness instead. Integration tests drive the HTTP surface through an
asynchronous \emph{httpx} client. The harness applies the evaluation
procedure to the golden data set, regenerates every table of Chapter~6
from a single manifest-pinned command, and accepts a measurement only
when the suite is green.

\hypertarget{deployment-and-operation}{%
\subsection{5.5 Deployment and
Operation}\label{deployment-and-operation}}

A single command (\emph{python scripts/run\_dev.py}) runs the pre-flight
checks and starts Uvicorn on port 8001 with hot reload. The service
binds to all interfaces (0.0.0.0) so that downstream components on the
same device can reach it, contacts no external service, and every
request still requires an API key; \emph{/health} reports Ollama
connectivity, the active model, the pipeline and the middleware
enablement map. A \emph{Dockerfile} (Python 3.11-slim, pinned
requirements) and a \emph{docker-compose} file (documented in the SRS)
provide a reproducible deployment alongside the Ollama runtime, with a
health check against \emph{/health}. The container runs a single worker
by design, because the in-memory cache and session store are per-process
state.

The administrative interface supports runtime reconfiguration without
redeployment: model switching, feature-flag reload, enforcement-policy
inspection, escalation resolution, audit summaries and engagement-scope
inspection. Rate limiting and command-length caps protect the model
backend, and these properties trace back to the trust boundary in
Chapter~4 and the threat model in Chapter~3.

In summary, the IRE is realised as a layered service whose behaviour is
verified by a deterministic suite of 506 passing tests and whose
configuration, integration interfaces and deployment are reproducible
from the committed sources. This verified baseline underpins the
measurements reported in Chapter~6.

\section{CHAPTER 6: RESULTS AND

This chapter reports the measured outcomes of the study and the evidence
used to validate the developed component. The evaluation used 1,500
records (600 well-formed and 900 flawed) and two model backends, Gemma
and Qwen. Results are organised around three research questions: RQ1

\hypertarget{chapter-7-discussion}{%
\section{CHAPTER 7: DISCUSSION}\label{chapter-7-discussion}}

This chapter interprets the measurements reported in Chapter~6 against
the research questions posed in Section~1.6. It compares the guardrail
stack with the baselines surveyed in Chapter~2, distinguishes the
research contribution from the product contribution, states the verified
limitations and threats to validity, and draws out the implications for
practice, for research and for the thesis itself. Section~7.1 interprets
the findings under each research question. Section~7.2 positions the
intent recognition engine (IRE) against existing solutions. Sections~7.3
and 7.4 set out the research and product contributions, Section~7.5
records the limitations and threats to validity, and Section~7.6 states
the implications.

\hypertarget{interpretation-of-findings}{%
\subsection{7.1 Interpretation of
Findings}\label{interpretation-of-findings}}

The guarded pipeline answers the central research question affirmatively
within a defined scope. A small, offline, unattended language model can
be made substantially more reliable as a gate for an automated security
copilot, provided that its output never reaches downstream tooling
before it has satisfied a conjunction of deterministic predicates. The
evidence for this claim is the experimental record reported in
Chapter~6. Its headline results are summarised against each research
question in Table~6.4 and are interpreted in turn in the subsections
that follow. The claim is bounded by the evaluated threat model and by
the residual miss rate: even in the full configuration, between 28\% and
36\% of flawed records were not caught (Section~7.5).

\hypertarget{rq1-pipeline-value}{%
\subsubsection{7.1.1 RQ1: Pipeline value}\label{rq1-pipeline-value}}

The unguarded model cannot be relied upon as an intent classifier. In
Experiment~1 (Section~6.1.1) the single-shot schema probe caught none of
the flawed records on either backend (a catch rate of 0\%), and its
false-positive rate on well-formed records was 32\% (Gemma) and 31\%
(Qwen). The guarded pipeline changes this profile (Table~6.1;
Figure~6.1): accuracy (D\textsubscript{Acc}) rose by 8 percentage points
for Gemma (78\% to 86\%) and by 13 for Qwen (69\% to 82\%), catch rose
from 0\% to 72\% and 64\%, and the false-positive rate fell by 18 and 16
points to 14\% and 15\%.

The accuracy gain is not the headline result. The more informative
movement is in the catch rate, which the guards raise from zero to
between 64\% and 72\% of all flawed records, while the false-positive
rate falls by roughly half (by 18 percentage points for Gemma and 16 for
Qwen). The most useful single reading of RQ1 is therefore the joint
nature of the two improvements: the deterministic stack adds the
capacity to detect flaws and, at the same time, reduces spurious
rejection, rather than trading one against the other.

Two cautions apply to this reading. First, the 0\% catch rate of the
unguarded baseline is largely a consequence of that configuration having
no mechanism for flagging flaws. It is a reference point and not an
empirical weakness of the model in its own right, and the more
discriminating evidence is the ablation analysis in Section~7.1.2.
Second, all figures are single-run point estimates (Section~7.5).

\hypertarget{rq2-layer-contribution}{%
\subsubsection{7.1.2 RQ2: Layer
contribution}\label{rq2-layer-contribution}}

Experiment~3 identifies the validation stack as the decisive component.
As Table~6.2 and Figure~6.2 show, removing the stack entirely lowers
catch from 72\% to 42\% for Gemma and from 64\% to 40\% for Qwen, which
are falls of 30 and 24 percentage points respectively. At the level of
individual layers, the hallucination validators make the largest
contribution to catch (9 percentage points for Gemma and 14 for Qwen).
This is consistent with the composition of the synthetic population, in
which fabricated parameters and Common Vulnerabilities and Exposures
(CVE) identifiers are the most frequent flaw kinds.

The design insight from Experiment~4 (Section~6.1.4) is that per-class
catch follows determinism. As Figure~6.3 illustrates, the classes that
expose a syntactic or enumerable signal (role-based access control
(RBAC) violations, adversarial phrasing, fabricated parameters and CVE
identifiers) are caught at 78--100\%, whereas the classes that require
the resolution of meaning (contradictory, out-of-scope and ambiguous
records) remain at 40--59\%. RQ2 is therefore answered at two levels. At
the layer level, the validation stack is decisive. At the class level,
the guard layers that contribute most are those that encode decidable
predicates, and the residual risk concentrates in the predicates that
are not decidable.

Table~6.2 also contains ablation rows in which catch rose, rather than
fell, when a guard was removed. Following the commitment made in
Section~3.5, these entries are interpreted as a removal-adversity
finding and not as a deficiency of the counterfactual treatment: the
default configuration concedes a small amount of catch in exchange for a
large preservation of usability, as measured by false positives and
accuracy. This reading is consistent with the framework of Chapter~2 and
does not contradict the safety invariant. It should nevertheless be
treated as behaviour of the committed single-run protocol and not as
evidence about the production setting, and its underlying mechanism
remains unconfirmed (Section~7.5).

\hypertarget{rq3-generalisability}{%
\subsubsection{7.1.3 RQ3: Generalisability}\label{rq3-generalisability}}

The ordering of catch-rate effects across the ablation rows is broadly
consistent across the two backends (Experiment~3). RQ3 is therefore
answered affirmatively for the safety dimension: within the two backends
evaluated, deterministic guardrailing rather than model choice is the
primary driver of catch-rate performance, provided that the trust
boundary remains closed. The size of the effects supports this reading.
The two backends differ by 8 percentage points in guarded catch (72\%
against 64\%), whereas the guards raise catch by 64 to 72 percentage
points over the unguarded baseline on each backend.

The accuracy dimension qualifies this conclusion. The accuracy
contribution of individual layers is backend-specific: the scope guard
dominates accuracy for Gemma, whereas the hallucination validator
dominates for Qwen. The generality claim must therefore be restricted to
the ordering of catch-rate effects (Section~3.5) and must not be
extended to the claim that any single layer is required, in the same
rank order, to preserve accuracy across backends. In summary, the
measured safety effect generalises across the two backends, whereas the
measured usability tuning does not.

The generation-side copilots, PentestGPT {[}1{]} and the

executor receives it. The measured catch rates of 72\% and 64\%
therefore do not compete with the task coverage of those systems. They
answer a question that those systems do not pose, namely what fraction
of flawed machine-bound decisions is caught before dispatch.

Fabrication-detection and agreement methods, namely SelfCheckGPT

verifier, it resolves the cost tension through a bounded-sampling
agreement gate and a deterministic escalation path, the hallucination
validator, which requires no large model (Section~2.3). The behaviour of
the semantic cache measured in Experiment~3 (Section~6.1.3) is what
makes this resolution practical on the constrained device.

demonstrated insufficiency of individual prevention techniques {[}4{]},
{[}5{]}, {[}16{]} is the strongest of the three. The surveyed defences
act as post-hoc, application-layer checks. The contribution of the IRE
is to compose its checks into a single stage that sits between
generation and dispatch (Figures~1.2 and 4.2), in which each predicate
(schema, syntax, network, scope and authorisation) is independently
decidable on a closed intent taxonomy. The ablation evidence that the
complete stack outperforms any single layer (Section~7.1.2) is the
empirical counterpart of this architectural difference, and it is the
reason the comparison is made at the level of a composed system rather
than of individual techniques.

\hypertarget{research-contribution}{%
\subsection{7.3 Research Contribution}\label{research-contribution}}

The research contribution is the answered question, not the artefact.
Three findings constitute it.

\emph{First}, the deterministic validation stack is the dominant driver
of the measured safety, and its effect is reproducible across the two
backends. The ablation evidence in Section~6.1.3 shows the stack
accounting for 30 and 24 catch points on Gemma and Qwen respectively,
against contributions of 9 and 14 points from the largest single layer,
and the same ordering holds on both backends. This turns the narrow
claim that ``guardrails help'' into a measurable ordering result: which
layers matter, and in which combination.

\emph{Second}, the effectiveness boundary is predictable: catch
concentrates on flaw classes that expose decidable structure. The
per-class catch spectrum of Section~6.1.4 runs from 100\% down to 40\%,
and its ranking follows the decidability ranking developed in the
conceptual framework (Section~2.5). This converts the limitation of
single-shot offline inference into a design principle for trustworthy
automation: in the closed-intent setting, a model should be asked for
structure and never for verdicts.

\emph{Third}, relative to the unguarded baseline, usability and safety
improve together. The guarded pipeline raises accuracy and catch while
roughly halving false positives (Section~6.1.1). The experimental record
therefore weakens the frequent implicit assumption that adding
deterministic checks to model output must trade precision for recall or
fluency for utility. The qualification is that this holds relative to
the unguarded baseline. Within the guarded design space, individual
layers do trade catch against usability, as the ablation rows discussed
in Section~7.1.2 show.

\hypertarget{product-contribution}{%
\subsection{7.4 Product Contribution}\label{product-contribution}}

The product contribution is the shippable IRE implementation developed
in Chapter~5 and exercised in the integration analysis of Section~6.4.
It is a guarded intent-recognition engine that converts free-form
offensive-security instructions into validated, schema-constrained and
authorised machine contracts end to end. Its measured and verifiable
properties are an automated test suite of 506 tests (434 unit and 72
integration tests, with 76\% statement coverage) that encode the safety
invariant as executable expectations, and a live C1--C2 contract
verification that exercised the real code paths (Section~6.4).

The differentiated value of the product lies in the stack rather than in
the model. The documentation and configuration of the engine define an
OWASP-aligned guardrail hardening, and its safety gate defines a
reject-or-warn path for every flaw class instead of rendering model
output downstream. Within the deployment constraints of offline,
CPU-only, single-inference and retrieval-free operation, none of the
designs surveyed in Table~2.1 provides the full conjunction of schema
checking, scope and authorisation enforcement and offline operation that
the product provides.

\emph{Single-run point estimates and the absence of confidence
intervals} are the principal internal-validity limitation. Each
configuration in Experiments~1--4 was executed once (Section~3.3), so no
measurement error or seed sweep bounds the deltas. The magnitudes of
individual layer effects, especially the small entries in which catch
rose when a layer was removed, must therefore be read as one-sample
observations. The protocol mitigates this limitation by committing the
execution in advance and fixing the data set, but it does not remove it.

\emph{Synthetic, non-uniform data} bound content validity. The
1,500-record population is generated against a committed taxonomy, and
its class sizes are non-uniform (600 D+ and 900 D− records, with
per-class sizes that also differ). Accuracy and catch figures are
therefore specific to this population and should not be read as
population-mean estimates for real production traffic.

\emph{A closed threat boundary} bounds external validity. The design
excludes retrieval and free-form rendering, which truncates the
indirect- and tool-injection channels by construction, but the
evaluation does not test threats outside this trust boundary: indirect
prompt injection, physical device compromise and backdoored model
weights were never presented to the engine. The claim is therefore
``reliable within the evaluated threat model'', not ``reliable
unconditionally''.

\emph{Hardware dependence.} All experiments ran on a single CPU-only
device, so conclusions about throughput, cache behaviour and feasibility
are single-platform observations. The hardware is recorded in the
reproducibility manifest (Section~3.7).

\emph{Number of backends.} Generalisation across backends rests on two
models, Gemma and Qwen. The consistent catch-rate ordering reported in
Section~7.1.3 is evidence of generality across these two cases only and
should not be extrapolated to other model families or sizes.

\emph{Unconfirmed mechanism.} The mechanism behind the rows in which
catch rose when a layer was removed is unconfirmed. It is attributed to
removal-adversity interactions, but no mechanistic study isolates it. It
is therefore flagged as open and not presented as explained.

\emph{Weak protection of semantic classes.} The three semantic flaw
classes (contradictory, out-of-scope and ambiguous) are caught at only
40--59\% because no deterministic signal exists for them. How to improve
these classes within the offline budget is left as an open research
question.

\emph{Engineering configuration caveats.} As stated in Section~7.4, the
default development API key and the dead production scope mode are
verified findings that materially affect deployment posture. They are
recorded as product limitations and are not conflated with the
evaluation.

\emph{Latency, energy and operational cost} are unmeasured throughout.
The evaluation prioritised correctness and catch, and an operator
deploying the engine should measure end-to-end latency on their own
hardware before committing to interactive use.

\hypertarget{implications}{%
\subsection{7.6 Implications}\label{implications}}

\hypertarget{implications-for-practice}{%
\subsubsection{7.6.1 Implications for
practice}\label{implications-for-practice}}

For practitioners deploying language models in security automation, the
strongest implication is architectural: place a deterministic, decidable
validation stage between a small offline model and machine dispatch, and
safety and usability can improve together, relative to an unguarded
model, rather than trade against each other. Under this
catch-before-dispatch posture the model is consulted for structure while
the system decides. The approach is directly actionable with offline
inference and a closed intent taxonomy, and it does not require a large
verifier model. The verified product gaps, namely the default
development credentials and the dead production scope route, should be
treated as design requirements for any similar engine before deployment.

\hypertarget{implications-for-research}{%
\subsubsection{7.6.2 Implications for
research}\label{implications-for-research}}

The measured ordering result answers the conditional reading of RQ3:
across the two backends evaluated, safety generalises whereas accuracy
tuning does not. This suggests that the research frontier lies less in
the choice of model than in the structure of the decidable predicates,
and it strengthens the case for composing model behaviour with
enumerable checks, rather than with sampling-based agreement, under
single-inference budgets. The weak protection of the three semantic
classes is the clearest open problem. Closing it within the offline
budget, for example through stronger structured prompting, targeted
enumerators or the bounded-sampling escalator, is a concrete direction
for future work. The single-run limitation should be removed by
repeating the committed protocol with seed sweeps and interval
estimates, which would convert the point estimates of this thesis into
bounded ones.

This thesis asked whether a small, offline language model can be made
reliable enough to drive an automated security copilot when its output
is subject to deterministic validation. Within a closed threat model,
the evidence indicates that it can. On the committed 1,500-record data
set, the guarded pipeline raised the flaw-catch rate from 0\% to
64--72\%, improved decision accuracy from 69--78\% to 82--86\% and
halved the false-positive rate to 14--15\% across two offline backends
(Experiment~1). Ablation showed that the deterministic validation stack
contributes most to safety (catch fell by 30 and 24 points when it was
removed), that safety transferred across backends while accuracy
contributions did not (Experiments~2 and 3), and that per-class catch
follows the decidability of the underlying predicate (Experiment~4).
Deterministic guardrailing, rather than model choice, therefore appears
to be the principal driver of measured safety.

The engine does not eliminate model error; it converts the open problem
of making a language model trustworthy into the closed problem of
classifying a single utterance under a known policy. The claim is
bounded by single-run point estimates, a synthetic and non-uniform data
set and a retrieval-free threat model.

\hypertarget{research-contributions}{%
\subsubsection{9.3.1 Research
contributions}\label{research-contributions}}

The research contribution has three parts. First, the deterministic
validation stack dominates measured safety across both backends, with
the hallucination validators the largest single layer (Experiment~3).
Second, catch effectiveness follows decidability, from 100\% on
structurally decidable classes to 40\% on meaning-dependent classes,
supporting a design principle: request structure from the model, never a
verdict (Experiment~4). Third, safety and usability improved together,
challenging the assumption that deterministic checks trade precision for
recall (Experiment~1).

\hypertarget{product-contributions}{%

contributions}\label{product-contributions}}

The product contribution is the IRE, an offline component whose output
is consumed by machines rather than reviewed by people, filling the gap
identified in the survey of existing systems. Its exportable properties
are the safety invariant, an audit-friendly structured response and a
506-test suite. Remaining configuration gaps (Table~9.2) do not affect
the evaluation, which used production credentials and strict scope
semantics.

\hypertarget{a.3-reproduction-procedure}{%
\subsection{A.3 Reproduction
procedure}\label{a.3-reproduction-procedure}}

The reported tables can be regenerated in five steps.

1. Obtain the committed project source, which includes the data set, its
generation script and the evaluation manifest.

2. Provision Ollama in CPU-only mode with the model builds pinned in the
manifest.

3. Run the automated test suite; a measurement is accepted only when the
suite is green.

4. Run the manifest-pinned harness command, which regenerates every
table of Chapter~6.

5. Compare the regenerated tables with the committed per-record
decisions.

Because the language model is stochastic, an independent re-run may
differ slightly from the committed values, whereas the deterministic
guards reproduce exactly. Absolute latency is bound to the evaluation
hardware (Section~3.7).
